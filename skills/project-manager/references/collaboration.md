# 分工、认领与交接

## 任务分工

在 TASK.md 中记录已确认的负责人、执行者与评审者。需要说明模块维护者时写在 CONTEXT.md 中，摘要维护方式写在 INDEX.md 中。Git 提交作者是历史贡献证据，不等于当前负责人；没有分工依据时保留 null，并汇报未分配工作。

TASK 的 owner 对交付负责，assignee 表示实际执行者，reviewer 表示评审者。同一人可承担多个角色，但需要独立评审的任务不能用作者自评伪装通过。外部任务系统已有权威分工时引用其记录，并明确本地记录的同步时间。

## 接手与并行工作

1. 阅读 INDEX、STATE、目标 TASK、来源想法或计划/接口、相关模块和最新参与者记录。
2. 检查依赖是否满足、任务是否已被认领、当前工作树是否含其他人的修改，以及声明范围是否与活跃任务重叠。
3. 复用团队已经采用的认领机制。文件模式在更新前重读 TASK、明确 assignee，并由任务维护者协调；不同机器尚未同步时无法保证认领互斥，向使用者说明这一实际限制。需要严格互斥时采用现有的事务任务系统或协调者串行分配。
4. 只有本次任务确实授权执行时才认领并实现。用户只要求规划或报告时不把所有 ready 任务改成 in_progress。
5. 参与者在 `records/{actor-session}.md` 写自己的记录，文件名使用唯一会话后缀，避免多个会话覆盖同一个人的记录。使用 [record.md](../assets/templates/record.md)。共享 TASK 的状态与交接由明确维护者整合，再刷新项目摘要。

不把 worktree 当作任务或接口互斥机制。独立工作需要代码隔离时遵循用户及项目已有 worktree/分支规则；出现相同文件修改时检查实际差异，保留双方工作，不通过覆盖另一份文件“解决”冲突。

创建子智能体、向其他聊天发消息或通知团队，分别遵守当前环境的授权规则；技能文件中的角色表和操作示例不授权派遣或发消息。

## 记录与交接

工作记录保留实际日期、参与者、结果、改动路径、版本/PR（有则填写）、检查方法和结果、未解决问题。不要填入假设成功的运行输出。

TASK 的交接部分必须足以回答：

- 当前实际完成了什么，哪些只实现未验证？
- 工作在什么分支/提交/工作树，是否还有未提交内容？
- 修改了哪些文件，有什么接口或数据影响？
- 检查了什么、结果怎样、尚缺什么条件？
- 下一步的具体动作与依赖是什么，谁应接手？

多人同时工作的停止位置保存在各 TASK；STATE 只汇总活跃任务入口，不用一个全局“上次停在哪里”覆盖所有工作流。

## 进度整合

核实记录后更新 TASK；汇总者只将相关任务结果汇入 STATE。找不到已确认维护者时可以在本次授权的管理操作中刷新本地摘要，并标注来源和核实范围，但不宣布自己成为长期团队负责人。

发生认领、责任、接口或修改范围冲突时记录具体冲突和可选解决办法。独立且不受影响的工作继续进行；阻塞的工作不靠等待时间或空白字段推定授权。
